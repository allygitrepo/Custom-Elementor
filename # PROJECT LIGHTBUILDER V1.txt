# PROJECT: LIGHTBUILDER V1

## Lightweight Visual Website Builder

Build a complete, production-ready, self-hosted visual website builder called:

**LightBuilder**

The application must allow a user to deploy the project to their own PHP-compatible hosting/server and then create, design, save, preview, and publish their own websites through a visual drag-and-drop editor.

The project must use:

* Frontend: React.js
* Backend: PHP
* Database: SQLite
* API: REST API
* Storage: Local filesystem
* Authentication: PHP backend sessions/token-based authentication
* Published website: Server-rendered/generated HTML/CSS/JS

The project must NOT depend on WordPress, Elementor, Laravel, Node.js on the production server, MySQL, or any external SaaS service.

The production server should only need:

* PHP
* SQLite support
* Apache/Nginx
* Basic filesystem write permissions

The React application is built during development and the generated production assets are deployed to the server.

---

# 1. PRODUCT VISION

The goal is to create a lightweight alternative to large website builders.

The user should be able to:

1. Deploy LightBuilder to their hosting.
2. Open the LightBuilder dashboard.
3. Create an account/admin user during first setup.
4. Create a website/project.
5. Open the visual builder.
6. Drag widgets onto a canvas.
7. Arrange containers and widgets.
8. Edit text/images/buttons.
9. Customize colors, typography, spacing, etc.
10. Preview the website.
11. Save the website.
12. Publish the website.
13. Open the published website through a public URL/domain.

The experience should be:

```text
Deploy
   ↓
Setup
   ↓
Login
   ↓
Create Website
   ↓
Open Builder
   ↓
Drag & Drop
   ↓
Design
   ↓
Preview
   ↓
Publish
   ↓
Public Website
```

The application must feel like a real product, not a demo.

# 7. DEPLOYMENT MODEL

The final application should be deployable to shared hosting.

Typical deployment:

```text
public_html/
│
├── index.php
├── .htaccess
├── client-build/
└── server/
```

However, structure the production build cleanly so that sensitive backend files are not directly exposed.

Prefer:

```text
public_html/
│
├── index.php
├── assets/
├── api/
├── published/
└── ...
```

with backend application code outside public access where hosting permits.

If shared hosting requires everything inside public_html, protect sensitive directories with `.htaccess`.

Provide a production deployment guide explaining both:

1. Apache/shared hosting
2. VPS/Nginx deployment

```text

BorderControl

```

Then widgets define their controls.

Example:

```javascript
{
    type: "heading",
    controls: [
        {
            name: "text",
            control: "text",
            label: "Heading"
        },
        {
            name: "tag",
            control: "select",
            options: [...]
        }
    ]
}
```

This is extremely important for maintainability.
